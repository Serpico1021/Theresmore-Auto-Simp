# 建造循环并发批量点击设计

## 背景

`getBuildSubpage().executeAction()`（`automation-src/base/Theresmore-Automation_4.14.4.base.user.js` 约47472-47623行）目前是严格串行的建造循环：每次只挑一个优先级最高的可建造按钮点击，点完调用 `waitForBuildingCountIncrease` 轮询等待该建筑真正建成（最多2秒、每100ms一次），确认成功后才重新取按钮列表进入下一轮；若这次和下一次都是人口敏感建筑（`isPopulationSensitiveBuilding`），中间还会额外插入一段与游戏真实节奏无关的固定 `await sleep(1400)`。

用户反馈：超转生（NG+）次数增多后，游戏内可连续建造的候选建筑经常同时大量出现（资源/产量加成让资源不再是建造瓶颈），此时串行"点一个等一个、人口敏感还要再等1400ms"的节奏成为明显的多余等待，拖慢了连续建造阶段的整体耗时。

已确认建筑本身存在真实的固定建造延迟（点击后过一段时间才在游戏状态里生效，不是点击即完成），因此不能简单粗暴去掉等待——正确的加速方式是**把多个不同类型建筑的等待时间并行化**，而不是消灭等待本身。

## 目标

- 同一轮里，把当前所有"可建造且建筑类型不同"的按钮一次性都点掉（不设固定数量上限），而不是一次只点一个。
- 只对这一批做一次等待，等到批次里各建筑各自的真实建成延迟都走完（或超时），而不是每个建筑各自等一遍再首尾相加。
- 去掉人口敏感建筑之间的固定 `sleep(1400)`，改为批次结束后按需调用一次 `adjustPopulation()`。
- 不读取、不依赖超转生次数这个具体数值；不区分玩家转生进度，对所有玩家一视同仁地去掉无意义的固定等待。

## 行为设计

### 批量轮次

1. 每一轮开始时，调用现有 `getAllButtons()` + `shouldBuildButton` 取出当前可建造的按钮集合（复用现状逻辑，不改变建筑列表/优先级排序规则）。
2. 按 `building.key` 去重：同一建筑类型在本轮只保留优先级最高的一个候选，避免同类型建筑在同一轮里被重复点击导致超建或重复统计。
3. 对去重后的候选集合逐个执行点击动作：
   - turbo 模式：直接调用 `state.MainStore.BuildingsStore.addBuilding(buildingKey)`。JS 单线程逐条同步执行，后一次调用发生时前一次已经完整跑完（包括游戏内部的资源扣减校验），不会出现资源超支的并发问题。
   - 非 turbo 模式：依次调用 `button.element.click()`，点击之间不再插入任何等待。
   - 点击前仍复用现有 `buttonWasUnavailable` 检查（`btn-off`/`disabled`），不可用的候选直接跳过，不计入本轮已点击集合。
4. 记录本轮实际点击的建筑集合（key → previousCount），进入统一等待阶段。

### 统一等待

- 新增批量版轮询（复用 `waitForBuildingCountIncrease` 的节奏参数：100ms 轮询间隔、2000ms 超时），但一次性检查本轮点击的**所有** building key：每轮询周期检查还有哪些 key 尚未达到 `count > previousCount`，全部达标则提前结束等待；超时后仍未达标的 key 标记为本次失败。
- 等待耗时 = 本批次中最慢的那个建筑的真实建成延迟，而不是逐个相加。
- 若 `!navigation.checkPage(CONSTANTS.PAGES.BUILD)` 或 `state.scriptPaused`，沿用现状逻辑提前结束等待并返回。

### 失败处理

- 单个建筑在批量等待里超时未达标（资源被同批次其他建筑抢完、容量不足、被游戏拒绝等），只将其从"本轮建成"集合中剔除，不再像现状那样让整个 `executeAction` 直接 `return`。
- 本轮建成集合为空（一个都没成功）时，视为本轮无有效进展，`return` 交还调度（与现状"建造失败即返回"的保守语义保持一致，避免死循环空转）。

### 人口敏感建筑交接

- 去掉现有"当前和下一个都是人口敏感建筑则 `sleep(1400)`"的整段逻辑。
- 本轮建成集合中没有人口敏感建筑时，不触发 `adjustPopulation()`，直接进入下一轮批量循环（复用现状"非人口敏感不触发调整"的语义）。
- 本轮建成集合中包含至少一个人口敏感建筑时，**不直接交接**——用批次等待结束后已经刷新过的 `buttons` 过滤 `shouldBuildButton`，检查下一轮候选里是否还有人口敏感建筑可建：
  - 还有：不调用 `adjustPopulation()`，直接进入下一轮批量循环继续建（跨多轮持续建造人口敏感建筑链，不因为已经点过一批就提前交接）。
  - 没有了（下一轮候选为空，或全是非人口敏感）：调用一次 `adjustPopulation()` 并 `return`，把后续非人口敏感建筑交给下一次调度处理。
  - 这一步是对 2026-08-30 批量人口敏感建筑设计（"连续多个人口敏感建筑之间不中断，直到下一个不再是人口敏感/不可建才交接"）的延续，只是把"看下一个单一按钮"换成了"看下一轮候选集合里还有没有"，批量化时不能省略这一步，否则会退化成"建一批就切人口页"，实机验证时已经踩过这个坑并修正。

### 不变的部分

- 首个 `common_house` + 首次农业研究（`completeFirstAgricultureResearch`）、`secureFirstFarmMaterials`、`guidedStart` 引导流程等特殊分支，继续在进入批量循环前单独处理一次，不纳入批量点击（这些分支有触发研究页跳转等副作用，塞进批量逻辑会显著增加复杂度且收益有限）。
- 建筑列表获取（`getBuildingsList`/`getAllButtons`）、优先级排序、`shouldBuildButton` 的安全锁判断逻辑均不改动。
- `state.buildings` 状态回填、`popAdjustBuildingList` 白名单维持现状。

## 实现边界

- 改动范围仅限 base 文件 `executeAction()` 内部的 `while` 建造循环本体：
  - 新增"按 key 去重 + 批量点击"逻辑替换现有的单一 `buttons.find(shouldBuildButton)` 取值方式。
  - 新增批量版等待函数替换单建筑版 `waitForBuildingCountIncrease` 的调用点（函数本身可保留供其他调用点使用，或改造为内部复用同一套轮询实现）。
  - 删除人口敏感建筑之间的 `await sleep(1400)` 分支，改为批次末尾按建成集合判断是否调用一次 `adjustPopulation()`。
- 不改动 fragments 内的建筑列表/人口规划逻辑（`smart-build-population-planner.js` 等）。
- 遵循项目既定三步校验流程：改完后依次执行 `automation-src/build.ps1` → `node --check` 校验产物语法 → `codemap regen --repo theresmore` 刷新索引。

## 风险与边界情况

- 非 turbo 模式下连续点击多个不同建筑按钮，中间不等待 React 重渲染：若某个按钮的可用状态（`btn-off`/`disabled`）依赖上一次点击已经生效的资源扣减，理论上存在"点击时判断可用、实际已不可负担"的竞态。按现状假设游戏点击处理函数本身会在内部校验花费合法性（不会因为客户端未及时刷新 disabled 态就允许真实超支建造），因此把这类点击标记为"本轮失败"即可，不需要额外的乐观锁或预先扣减模拟。
- 批量点击不设数量上限：理论上如果某一轮可建造的不同类型建筑数量很多，会在极短时间内连续触发很多次点击/store 调用。暂不做限流，后续如观察到实机异常（例如触发游戏侧的速率限制或界面卡顿）再补充节流。

## 测试

- 手工在实机验证：①超转生多次后进入连续建造阶段，观察是否出现"多个不同建筑几乎同时建成"的现象，且没有出现超建/资源透支/建筑数量误判；②人口敏感建筑批次建成后能正确触发一次人口调整，不会遗漏也不会对同一批次重复触发；③首个普通房屋+农业研究流程不受影响。
- 无自动化测试覆盖（本项目 base 文件无既有单测基础设施），依赖实机观察日志（`logger` 输出）确认批次点击、批次等待结果与人口调整触发时机符合预期。
